# Spec Kit: Конституция фичи для Task Planner (practice_04/task_planner)

## Базовые принципы (неизменяемые)

1. Стабильный публичный контракт
   - Сохраняем публичный API и модель `Task`, описанные в `AGENTS.md` и `docs/requirements.md`.
   - Стабильные эндпоинты: `GET/POST /api/tasks`, `PUT/PATCH/DELETE /api/tasks/:id`.

2. Отсутствие регрессий в существующем поведении
   - Сохраняем существующие функции планировщика и текущее поведение UI/сервера.

3. Клиентская фильтрация
   - Фильтрация выполняется на клиенте по уже загруженным задачам (`GET /api/tasks`).
   - Серверный контракт не меняется; новые серверные эндпоинты не требуются.

4. Нулевые новые зависимости в рантайме сервиса
   - Не добавляем внешние npm-зависимости в Node.js-сервис; используем нативные средства.

5. TDD как обязательный процесс
   - Сначала тесты, затем реализация (Red → Green → Refactor), используя скилл `test-driven-development`.

6. Неприкосновенность инфраструктурных артефактов
   - Не меняем `scripts/check.sh` и `docs/requirements.md`.

7. Документация фичи
   - Документацию фичи размещаем в артефактах Spec Kit (этот файл и спецификации) и дублируем ключевые положения в `practices/practice_04/task_planner/docs/HANDOFF.md`.

8. Гейт на реализацию
   - Реализацию начинаем только после согласования человеком спецификаций UI и логики (Spec Kit артефакты, список сценариев и критерии приёмки).

## Ограничения и совместимость

- Формат объекта `Task` и временные поля (ISO 8601 UTC) неизменны.
- Источник данных — `data/tasks.json`; любые изменения формата требуют безопасной миграции без поломок старых данных.
- CORS и лимиты тела запроса — как в текущем сервисе; ужесточения возможны только по контракту.

## Рабочий процесс (workflow)

1. Спецификация
   - Подготовить Spec Kit артефакты: UI-спецификация, сценарии взаимодействия, критерии приёмки, тест-план.
   - Получить явное согласование человеком.
2. Тесты
   - Добавить или уточнить тесты, покрывающие спецификацию, без изменений реализации.
3. Реализация
   - Минимальные правки для прохождения тестов, без добавления новых рантайм-зависимостей.
4. Документация и handoff
   - Обновить Spec Kit и `docs/HANDOFF.md` при необходимости.
5. Проверка
   - `sh scripts/check.sh` должен завершаться успешно.

## Управление (governance)

- Данная Конституция обязательна для всех изменений, относящихся к фичам в `practices/practice_04/task_planner`.
- Любые отступления требуют отдельного письменного поручения и обновления Spec Kit.
- При ревью проверяется соблюдение принципов, TDD и обратной совместимости.
