# Руководство для агента по реализации фич

Этот документ — источник правды для реализации и расширения сервиса планировщика задач и дедлайнов, расположенного в `practices/practice_04/task_planner`.

Минимальные указания (обязательно к соблюдению):
- Контракт: docs/requirements.md
- Пример теста: tests/test_example.py
- Проверка: sh scripts/check.sh
- Не меняй контракт и runner без поручения.

## Обзор сервиса
- Путь: `practices/practice_04/task_planner`
- Стек: Node.js 18+, без внешних npm-зависимостей
- Точка входа: `server.js`
- Хранилище: файл `data/tasks.json` (JSON-массив)
- Фронтенд: статические файлы из `public/` (`index.html`, `styles.css`, `app.js`)
- Порт по умолчанию: `3000` (настраивается переменной окружения `PORT`)

## Публичный API (стабильный контракт)
Все ответы API — JSON. В случае ошибки возвращается `{ "error": "<сообщение>" }`.

1. GET `/api/tasks`
   - Описание: вернуть массив задач.
   - Код 200: `[{Task}]`

2. POST `/api/tasks`
   - Описание: создать новую задачу.
   - Тело: `{ title: string, description?: string, priority?: 'low'|'normal'|'high', deadline?: ISOString }`
   - Код 201: `{Task}`
   - Ошибки: 400 при невалидном JSON или отсутствии `title`.

3. PUT/PATCH `/api/tasks/:id`
   - Описание: частичное/полное обновление задачи.
   - Тело (любые из): `{ title?, description?, priority?, deadline?, done? }`
   - Код 200: `{Task}`
   - Ошибки: 404 если задача не найдена.

4. DELETE `/api/tasks/:id`
   - Описание: удалить задачу.
   - Код 200: `{Task}` (удалённая)
   - Ошибки: 404 если задача не найдена.

Модель `Task`:
```
{
  id: string,                // стабильный идентификатор
  title: string,             // обязательное поле
  description: string,
  priority: 'low'|'normal'|'high',
  deadline: string|null,     // ISO 8601 (UTC) или null
  done: boolean,
  createdAt: string,         // ISO 8601 UTC
  updatedAt: string          // ISO 8601 UTC
}
```
Замечания по времени и TZ: фронтенд вводит `datetime-local` (локальная зона), сервер сохраняет ISO в UTC; преобразование делает клиент.

## Будущие фичи (простые)
Фичи ниже добавляются без изменения текущего публичного контракта API.

1) Поиск и фильтрация на клиенте
- UI: добавить поле поиска по подстроке (название/описание) и выпадающий фильтр по приоритету (low|normal|high|all).
- Реализация: фильтрация выполняется на фронтенде по уже загруженному списку (`GET /api/tasks`).
- Контракт API не меняется.

2) Массовые действия над задачами
- UI: чекбоксы у задач для выбора нескольких элементов и кнопки "Отметить выполненными" и "Удалить выбранные".
- Реализация: фронтенд вызывает существующие эндпоинты `PUT /api/tasks/:id` и `DELETE /api/tasks/:id` последовательно для выбранных задач.
- Контракт API не меняется; дополнительных серверных эндпоинтов не требуется.

## Используемый скилл
При разработке применяй только скилл "test-driven-development" для TDD-подхода: сначала пишем (или уточняем) тесты, затем реализуем минимальную функциональность для их прохождения. В рантайме сервиса внешние скиллы не используются.

## Требования к изменениям и совместимости
- Публичный контракт, описанный выше, менять нельзя без явного поручения.
- Дополнения должны быть обратно совместимыми: новые поля — опциональны; новые эндпоинты не ломают старые.
- `id` задач стабилен; формат времени — ISO 8601 UTC.
- Источник данных — `data/tasks.json`. При изменении формата — миграция читается безопасно и не ломает старые данные.
- Не добавляй тяжёлые зависимости в Node-сервис без необходимости; приоритет — нативный Node и вызов внешних скиллов.

## Что менять можно
- Внутреннюю реализацию `server.js`, структуру модулей и фронтенд в `public/` при сохранении контракта.
- Добавлять новые эндпоинты и элементы UI, не затрагивая стабильные.
- Улучшать обработку ошибок/валидацию/логирование.

## Что менять нельзя (без явного поручения)
- Контракт: `docs/requirements.md`.
- Runner и сценарии проверки: `scripts/check.sh` и сопутствующие договорённости (порты, формат логов).
- Стабильные эндпоинты: `/api/tasks`, `/api/tasks/:id`.
- Формат объекта `Task` и типы его полей.

## Проверка результата
Запуск автоматической проверки:
- `sh scripts/check.sh`

Ожидаемый пайплайн проверки:
1. Запуск сервера на свободном порту (возможен экспорт `PORT` в окружение). Допустима проверка готовности через GET `/api/tasks`.
2. Запуск тестов, включая пример: `tests/test_example.py`.
   - Подход: black-box HTTP тестирование (например, Python requests).
   - Базовые проверки:
     - Создание/чтение/обновление/удаление задач.
     - ISO UTC формат временных полей.
     - Корректные статусы ошибок 400/404.
   - Для простых фич UI допускается проверка наличия базовых элементов во фронтенде по статическим файлам:
     - В `public/index.html` присутствуют элементы управления для поиска и фильтрации (например, `#search`, `#priority-filter`).
     - В `public/index.html` присутствуют элементы для массовых действий (например, `#bulk-complete`, `#bulk-delete`).
3. Корректная остановка сервера после тестов.

Критерии приёмки:
- Все тесты проходят; `scripts/check.sh` завершается с кодом 0.
- Существующие эндпоинты и фронтенд работают без регрессий.
- Новые фичи используют внешние скиллы, задокументированы в `docs/requirements.md` и покрыты тестами.

## Примечания по качеству
- Ограничение на тело запроса ~1MB; при переполнении возвращать 400.
- CORS: текущая политика `*` для простоты локальной разработки; ужесточения — только по контракту.
- Сообщения об ошибках — краткие и информативные.

## Навигация по коду
- `practices/practice_04/task_planner/server.js` — сервер и API.
- `practices/practice_04/task_planner/public/` — фронтенд (UI).
- `practices/practice_04/task_planner/data/tasks.json` — данные (создаётся автоматически при запуске).
- `practices/practice_04/task_planner/docs/style-guide.md` — правила для фичи поиска/фильтрации (прочитай перед изменениями фронтенда).
