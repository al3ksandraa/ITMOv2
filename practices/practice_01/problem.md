# Проблема и метрики

## Проблема

- Пользователь: клиент HTTP API (разработчик или сервис), отправляющий diff pull request для автоматического ревью.
- Ситуация: клиент вызывает POST /api/reviews с телом JSON и ожидает предсказуемый ответ с замечаниями по diff.
- Что происходит сейчас: в обработчике POST /api/reviews используется параметр payload: dict и прямой доступ payload["diff"] (app/api.py 35-37); в ReviewService формируется промпт "Review this pull request and find problems:\n{diff}", вызывается LLM.generate, и возвращается словарь {"comment": <строка>} (app/review_service.py 19-22).
- Почему это мешает пользователю или бизнесу: отсутствие валидации тела запроса может приводить к 500 при отсутствии/неверном поле diff; неограниченный diff увеличивает риск ошибок/задержек на стороне LLM; формат результата не закреплён схемой, что снижает предсказуемость для клиентов.
- Что не входит в задачу: внесение изменений в код; выбор LLM-провайдера; аутентификация и лимитирование. В этой задаче фиксируются проблемы и требования в документах.

## Метрики

Выберите измеримые показатели, относящиеся к проблеме. Не используйте VTG, IRR, WACC, CSAT или другую метрику только ради названия.

| Метрика | Текущее значение или способ замера | Целевое изменение | Когда измеряем | Источник данных |
|---|---:|---:|---|---|
| Доля 5xx на POST /api/reviews при отсутствии поля diff | Вызовы без ключа "diff" приводят к KeyError и 500 (обосновано кодом) | -> 0%; ожидать 422 | После добавления валидации (план) | Ручные вызовы/логи |
| Доля ответов в формате {"comment": str} | Ручная проверка по примерам | -> 100% | Регулярно | Ручные проверки |

## Почему изменение метрики подтвердит решение проблемы

Снижение 5xx на невалидных запросах подтвердит корректную обработку входа. Доля ответов, соответствующих контракту, покажет стабильность и предсказуемость API.
